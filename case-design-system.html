CASE STUDY · DESIGN SYSTEMS

Completing a half-built design system, and keeping three platforms honest

Digidentity verifies government-issued identity across web, iOS and Android, a domain where an inconsistent component or a broken translation isn't a polish problem, it's a trust-and-compliance one. I co-founded the V7 design system, inherited it outright when the founding designer left three months in, and, as the sole designer, grew a partial foundation into the system behind the company's web auth experience and both mobile apps.

Context: Digidentity is an eIDAS Qualified Trust Service Provider on the EU Trusted List. Its design system spans a Ruby on Rails web stack (AuthBox and the Self-Service Portal) and native iOS and Android apps.

The Discovery

The Problem

Three months into my time at Digidentity, the company had the start of a design system, a partial component set and a token foundation, and then lost the person building it. Design systems don't mature in three months. As the only designer across web, iOS and Android, I inherited an unfinished system and the job of completing it, expanding it on a strict atomic structure, and stopping three separate codebases from drifting apart.

A design system's real users are engineers. Mine were two web teams, the Ruby on Rails developers behind AuthBox and the Self-Service Portal, and the mobile engineers, plus the end users verifying identity across devices and languages.

Constraints I Designed Within

01A regulated eIDAS environment, where visual consistency is itself a trust signal, not a nice-to-have.
02Three codebases with no shared rendering layer: web (Rails), iOS and Android could each drift independently.
03A multilingual UI, Dutch and English on AuthBox, where longer translations must not break fixed layouts.
04No design peer. Every component decision was mine to make, document and maintain.

Strategy & Logic

Atomic Structure as a Survival Strategy

With one designer and three platforms, the only way to keep velocity without fragmentation was strict atomicity: every new component composes from shared primitives and tokens, so consistency is structural rather than manual. The Figma UI Kit is the single source of truth, define once, consume everywhere.

The Pivot

A half-built system carries invisible debt. As I extended it, the token layer revealed classic drift, the exact inconsistency a design system exists to prevent. The same red lived under three different names. Semantic tokens collided with raw brand names. The type scale had gaps the code didn't cover, and Figma no longer matched the AuthBox front end. The colour page was literally titled "in progress".

The fix wasn't more components. It was a real source of truth.

Duplicate values and hand-maintained aliases don't scale for a sole owner across three codebases; tokens have to generate from one origin. I diagnosed the debt and scoped the consolidation now underway: collapse the duplicates, reconcile Figma against the code, and move to a Figma Variables → Style Dictionary pipeline so every platform builds from one set of tokens. The lesson I carry forward: treat the token pipeline as foundational infrastructure from day one, not a later clean-up.

Typography: two systems that didn't agree

Colour was the obvious drift; typography was the deeper one. Figma described type in semantic roles — Hero, XXL, XL, L, Card title, Body, Hint — while the SCSS described the same type in a t-shirt scale ($font-size-lg → 4xl). A designer reading Figma and a developer reading the stylesheet were naming the same thing two different ways, and the two had quietly fallen out of sync.

I audited the Figma scale against the live AuthBox build, role by role and breakpoint by breakpoint. What it surfaced:

no such size in scssFigma's Hero sizes had no equivalent in the stylesheet, across all three breakpoints — the largest, most visible type existed only in design.
diff sizeFigma and SCSS disagreed on the actual pixel sizes at roughly seven steps (XL, L and Card title across breakpoints), so the same role rendered differently in design and in code.
no body variableThe most-used style on the platform — body text — had no token at all. It was hard-coded rather than referenced from the system.
check authboxEvery mismatch was verified against the running product, not assumed from the file, so the reconciliation reflected what users actually saw.

The fix is the same as for colour, and it's why the token pipeline matters: one source generating both the Figma variables and the SCSS, with a single role vocabulary and a real token for every style — including the body text that never had one.

The Execution

A System That Ships, Not a Library That Sits

The proof point
  • The system ships as a Rails gem plus shared NPM packages, and both AuthBox and the Self-Service Portal consume the same library, so a token or component change propagates from one source instead of being rebuilt per project.

Components were specified for every state and validated in isolation before landing in product, the mobile team maintained a dedicated "UI Component Kit" sample app for exactly this. Hardening the web components with the Rails engineers took roughly four months of component-level testing and fixing.

Accessibility & Internationalisation

Semantic colour tokens were checked for WCAG contrast so consistency and legibility hold together; focus, keyboard and disabled states are specified at the component level; and components handle Dutch and English, where longer strings must not break fixed layouts.

The Conclusion

Results

The V7 system now underpins the AuthBox web auth experience, a unified login and account-creation flow, and the Self-Service Portal, both consuming one shared component library, alongside the iOS and Android apps. The AuthBox migration shipped incrementally and low-risk. The token consolidation is the current work: closing the gap between Figma and code so the single source of truth is truly single.

Reflections

Inheriting a half-built system taught me that a design system's hardest problem isn't the components, it's governance with no design peer. Duplicate tokens and Figma-to-code drift are what happen when a system grows faster than its source of truth. Next time I'd treat the token pipeline as foundational infrastructure from day one.
